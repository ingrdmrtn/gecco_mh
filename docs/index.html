What is GeCCo?

GeCCo (Guided Generation of Computational Cognitive Models) is a research pipeline that uses Large Language Models (LLMs) to automatically write, fit, and improve computational models of how people make decisions.

🧠 Generate

An LLM writes candidate cognitive models as Python functions, guided by the task description, example participant data, and guardrails.

📊 Fit

Each generated model is fitted to real participant data using maximum likelihood estimation (multi-start L-BFGS-B).

📈 Evaluate

Models are ranked by information criteria (BIC / AIC). Parameter recovery, posterior predictive checks, and individual-differences analyses are run automatically.

🔄 Iterate

A structured feedback loop tells the LLM what worked and what didn’t, guiding it to propose better models in the next round.

Why does this matter?

Computational cognitive models are the standard tool for understanding the mental processes behind human decision-making. But writing them by hand is slow, biased by the modeler’s intuition, and hard to scale. GeCCo automates model discovery, letting you explore a much wider space of possible models and find ones you might never have thought of.

The pipeline at a glance

Task description
+ data → LLM generates
model code → Fit to participant
data (L-BFGS-B) → Evaluate &
rank (BIC) → LLM judge gives
structured feedback → Repeat
N iterations

The judge is itself an LLM that analyses the full history of models and results, then writes detailed feedback about what to try next — which parameters matter, which mechanisms are promising, and what’s still missing.

Key features

  • Task-agnostic — works with any behavioural task that produces trial-level choice data
  • LLM-agnostic — supports OpenRouter, OpenAI, Gemini, vLLM, HuggingFace models, and more
  • Distributed — run many search clients in parallel across an HPC cluster
  • Interpretable — every model is a standalone Python function you can read, modify, and reuse
  • Reproducible — all results tracked in a DuckDB registry with full audit trail

Quick Start

Prerequisites

  • Python ≥ 3.10, with uv (or pip / conda as alternatives)
  • An OpenRouter API key (or alternative provider, see Backends)
  • Basic familiarity with the command line and Python

Installation

git clone https://github.com/MilenaCCNlab/gecco.git
cd gecco
uv sync                       # install all dependencies (recommended)
# or: pip install -r requirements.txt

Set your API key

Create a .env file in the project root (it is already in .gitignore):

# OpenRouter gives you access to 200+ models via a single API key
OPENROUTER_API_KEY=your_openrouter_api_key_here

Get an OpenRouter API key from openrouter.ai/keys.

Run a local search

uv run python -m gecco run local-client --config config/archive/two_step_factors_gemini3flash.yaml

This will:

  1. Load the two-step task config
  2. Prompt the LLM (via OpenRouter) to generate a cognitive model
  3. Fit it to participant data using L-BFGS-B
  4. Compute BIC and save results to results/
  5. Repeat for the configured number of iterations

Monitor progress

uv run python -m gecco monitor --watch 10

Annotated example

Below is a real config file for the two-step decision task using Gemini 3 Flash:

# ---- TASK ----
task:
  name: "two_step_factors"
  description: |
    In this task, the participant makes a sequence of choices
    to earn money. Each trial: choose between two images, which
    probabilistically transition to a second-stage screen,
    then choose again for a reward.
  goal: |
    Propose {models_per_iteration} new cognitive models
    as Python functions: {model_names}

# ---- DATA ----
data:
  path: "data_g_2019/preprocessed_study2_no_baseline.csv"
  id_column: "participant"
  input_columns: ["choice_1", "state", "choice_2", "reward"]
  narrative_template: |
    The participant chose spaceship {choice_1}, traveled to
    second stage state {state}, made choice {choice_2}, and
    received {reward} coins.
  value_mappings:
    choice_1: {"0": "A", "1": "U"}
    state:    {"0": "X", "1": "Y"}
    choice_2: {"0": "W", "1": "S"}
  splits:
    prompt: "[1:3]"   # first 3 participants used as examples

# ---- LLM ----
llm:
  provider: "openrouter"      # or "gemini", "openai", "vllm" etc.
  base_model: "google/gemini-3-flash-preview"
  temperature: 0.2
  max_tokens: 16384
  models_per_iteration: 1
  include_feedback: true
  guardrails:
    - "Each model must be a standalone Python function."
    - "Function names: cognitive_model1, cognitive_model2, ..."
    - "Return the negative log-likelihood of observed choices."
    - "Include a clear docstring with parameter bounds."
    - "Use @njit decorator (Numba). No axis= arg on np.max/min."

# ---- EVALUATION ----
evaluation:
  metric: "bic"
  optimizer: "L-BFGS-B"
  eval_test_split: 0.7       # 70% train, 30% held-out test

# ---- LOOP ----
loop:
  max_iterations: 20
  n_clients: 9

# ---- JUDGE ----
judge:
  mode: "llm"
  context:
    attempted_models: true
    performance: true
    best_model_code: true
    diagnostic: false
  output:
    persona_synthesis: false
  ppc:
    enabled: true
    n_sims: 100

Judge System

The judge is an LLM-powered analyst that examines the full history of generated models, their fit results, parameter recovery, posterior predictive checks, and individual-differences regressions, then writes structured feedback to guide the next iteration of model generation. It is the engine behind the “Iterate” step of the pipeline.

How the judge works

The judge behaviour is controlled by three fields: mode, context, and output. Depending on the mode, the judge either returns deterministic context directly (static), calls an LLM with non-tool context (llm), or runs a tool-enabled LLM agent (agent). The context section controls which information areas are available (attempted models, performance, code, diagnostics). The output section enables optional persona-specific synthesis. See the tables below for the full schema.

In all modes except agent, information is gathered deterministically from the diagnostic store without LLM tool calls. In agent mode, the LLM may call read-only tools whose availability is strictly gated by the enabled context fields — tools beyond the configured context are rejected at the dispatch level.

Mode, Context & Output

The judge behaviour is controlled by three fields under judge: mode, context, and output.

Mode

judge.mode selects the overall judge strategy:

ModeWhat it does
"off" No feedback is produced. The judge short-circuits immediately. Useful for testing or disabling the judge.
"random" Returns a fixed text urging creative exploration without any analysis. Tool calls and LLM analysis are completely skipped. Useful as a control condition. No context fields may be enabled.
"static" Deterministic feedback based on enabled context sections only. No LLM calls, no tool calls, no recommendations. Produces a deduplicated model-name list (when attempted_models is enabled) and/or a metric-only summary (when performance is enabled).
"llm" Assembles deterministic context from enabled judge.context fields, then asks an LLM to summarise and recommend. No tool schemas are exposed. Prompt messages include only the enabled context.
"agent" Full tool-using LLM pipeline. The LLM queries the diagnostic store via read-only tools. Only tools allowed by judge.context are exposed. Requires at least one enabled context field.

Context

judge.context controls which information sections are available to the judge (all are booleans, default false):

FieldWhat it controls
attempted_models When enabled, the judge receives a deduplicated list of model names attempted in the current iteration. In static mode this is the only content produced when used alone. In llm/agent modes, model names are included in the prompt context.
performance When enabled, the judge receives BIC values, trajectory, and fit status. In static mode, contributed a metric-only summary. In llm/agent modes, performance data is included in the prompt. Does not include model names, code, or diagnostics.
best_model_code When enabled, the best model's Python source code is appended to the feedback text, giving the LLM concrete code to build upon. Only applies in static, llm, and agent modes (never in off or random).
diagnostic When enabled, the judge receives detailed diagnostic sections (PPC, posterior predictive checks, block residuals, parameter recovery). In llm and agent modes, the judge prompt includes dedicated diagnostic analysis angles and the corresponding tool schemas (in agent mode).
individual_differences When enabled, the judge receives participant-level fit heterogeneity and self-report regression (R²) evidence. In llm and agent modes, the prompt includes an individual differences analytical angle. In agent mode, the get_individual_differences and get_participant_best_models tools become available.

Output

judge.output controls additional output formatting:

FieldWhat it controls
persona_synthesis When enabled and 2+ personas are configured, the judge generates persona-specific feedback tailored to each client profile's search strategy (e.g. one feedback for the “exploit” client, another for “explore”). Requires explicit judge.persona_profiles or client-level feedback_guidance.

Analytical angles

The analytical dimensions available to the judge depend on the enabled judge.context fields:

  1. Statistical fit quality — Available when context.performance is enabled. Compares top models by BIC, identifies improvement, plateau, or regression, and examines per-participant model preferences and outliers.
  2. Parameter identifiability — Available when context.diagnostic is enabled. Checks parameter recovery for the best models and identifies which parameters are well-recovered vs problematic.
  3. Predictive adequacy — Available when context.diagnostic is enabled. Inspects posterior predictive checks (PPC) and block-level residuals to identify which aspects of the data the models capture or miss.
  4. Individual differences — Available when context.individual_differences is enabled. Compares R² across models when regressing parameters against self-report questionnaire scores, and examines participant-level model heterogeneity.
  5. Mechanism interpretability — Available when context.best_model_code is enabled. Reads the code of best and failed models and assesses psychological interpretability and parsimony.
  6. Search breadth — Available when context.attempted_models is enabled. Identifies mechanisms tried-and-failed vs tried-and-succeeded vs not-yet-explored across model families.

Diagnostic tools

In agent mode, the judge has read-only tools for querying the DuckDB diagnostic store. The available tools are gated by the enabled judge.context fields — for example, diagnostic tools (PPC, recovery, residuals) are only available when context.diagnostic is enabled, individual-differences tools (get_individual_differences, get_participant_best_models) only when context.individual_differences is enabled, and performance tools (BIC trajectory, fit status) only when context.performance is enabled. Tools outside the configured context are rejected at the dispatch level even if the LLM requests them.

Mode behaviour summary

The mode determines what the judge does and which context it uses:

  • "off" — No feedback. All context ignored.
  • "random" — Fixed exploration text. All context must be disabled.
  • "static" — Deterministic context sections only, no LLM calls, no tool calls, no recommendations.
  • "llm" — Context-assembled LLM synthesis, no tool schemas, recommendations always included.
  • "agent" — Full tool-using LLM pipeline, context-gated tool schemas, requires at least one context field.

Configuration example

judge:
  mode: "agent"                # full tool-using LLM pipeline
  context:
    attempted_models: true     # include model names
    performance: true          # include BIC and trajectory
    best_model_code: true      # append best model source code
    diagnostic: true           # include recovery, PPC, block residual angles
    individual_differences: true # include R² and participant heterogeneity
  output:
    persona_synthesis: false   # single feedback for all personas
  ppc:
    enabled: true
    n_sims: 100
  diagnostic_store:
    enabled: true

Data Format

GeCCo expects trial-level behavioural data as a CSV with one row per trial. The required columns depend on your task, but the standard setup uses:

ColumnMeaningValues

trialTrial number within participantInteger
choice_1First-stage choice0 or 1
stateSecond-stage state reached0 or 1
choice_2Second-stage choice0 or 1

Data splits

Participants are split into three groups:

  • Prompt set — shown to the LLM as example narratives (typically first 2–3 participants)
  • Training set — used for model fitting (e.g. 70%)
  • Test set — held out for final evaluation (e.g. 30%)

Splits are configured in YAML using slice notation like "[1:3]" (first 3 participants) or "[4:]" (all remaining).

Optional: individual differences data

If you have self-report questionnaire data, GeCCo can automatically regress each model’s best-fitting parameters against questionnaire factors to see which cognitive mechanisms correlate with individual traits:

individual_differences_eval:
  data_path: "data_g_2019/self_report_study2.csv"
  predictors: ["Factor1", "Factor2", "Factor3"]
  covariates: ["age", "gender"]

Entrypoints

GeCCo is a Python package run from the command line. The main entrypoint is:

python -m gecco <command> [<subcommand>] [args]

When using uv, prefix with uv run (e.g. uv run python -m gecco ...). HPC SLURM jobs resolve the environment manager automatically.

CLI commands

CommandSubcommandWhat it does
runlocal-clientSingle local run for testing/debugging. Great place to start.
rundistributedLaunch a full distributed run across SLURM. The config selects regular or CMG mode; GeCCo connects to an external vLLM if needed.
internaljudge-orchestrateInternal judge orchestration for SLURM-managed feedback and structured results.
monitor—Monitor a running experiment. Add --watch N for a live-refresh dashboard.
reset—Reset / clean a run’s state (removes DuckDB files and artifacts).
internaldistributed-clientInternal entrypoint for SLURM-launched clients. You won’t call this directly.
internaltest-evaluationRun the final test-set evaluation after all clients finish.

Examples

# Local test run (no HPC needed)
uv run python -m gecco run local-client --config config/archive/two_step_factors_gemini3flash.yaml

# Launch distributed run on SLURM (uses configured provider — no GPU node needed)

Programmatic API

You can also use GeCCo from Python directly:

from config.schema import load_config
from gecco.prepare_data.io import load_data, split_by_participant
from gecco.prepare_data.data2text import narrative
from gecco.load_llms.model_loader import load_llm
from gecco.run_gecco import GeCCoModelSearch
from gecco.prompt_builder.prompt import PromptBuilderWrapper

cfg = load_config("config/two_step_factors/deepseekv4flash/judge_off.yaml")
df = load_data(cfg.data.path, cfg.data.input_columns)
splits = split_by_participant(df, cfg.data.id_column, cfg.data.splits)
data_text = narrative(splits["prompt"], cfg.data.id_column, cfg.data.narrative_template)

prompt_builder = PromptBuilderWrapper(cfg, data_text)
model, tokenizer = load_llm(cfg.llm.provider, cfg.llm.base_model)

search = GeCCoModelSearch(model, tokenizer, cfg, splits["eval"], prompt_builder)
best_model, best_bic, best_params = search.run_n_shots(run_idx=0)

print("Best BIC:", best_bic)
print("Best params:", best_params)

Hardware Requirements

How much hardware you need depends almost entirely on which LLM backend you choose. There are two main paths:

Path 1: API-based (no GPU needed) — recommended

With OpenRouter (or Gemini, OpenAI, etc.) you don’t need a GPU at all. GeCCo sends prompts to the cloud provider and fits models on your CPU. This is the simplest and most reliable setup:

  • An internet connection
  • An API key (OpenRouter gives you access to 200+ models, including Gemini, GPT, DeepSeek, Claude, and Llama, all through one key)
  • Enough RAM for your participant data (8–16 GB is plenty)
This is the recommended path for everyone. Set provider: "openrouter" in your config and you’re done.

Path 2: Local / self-hosted models (GPU optional)

If you need to run everything without external API calls, you have two options:

Local HuggingFace models

Load a model directly in-process via HuggingFace Transformers. You need a CUDA-compatible GPU with sufficient VRAM:

Model sizeParametersVRAM (bfloat16)Min GPUs (40 GB A100)
Tiny (test)1.5B≈3 GB1
Small3–8B≈6–16 GB1
Medium14B≈28 GB1
Large32B≈64 GB2
Very large70–72B≈140–144 GB4

Models load with device_map="auto" to spread across GPUs. Set HF_HOME to a scratch filesystem on HPC to avoid filling your home directory.

Self-hosted vLLM server (advanced)

Instead of loading a model in-process, serve it as a standalone API via vLLM on a GPU node, then point GeCCo at it over HTTP. This decouples serving from fitting so CPU-only nodes can query one shared GPU-backed model server. Configure via provider: "vllm" and VLLM_BASE_URL.

Running on HPC / SLURM

When model fitting is the bottleneck (e.g. fitting hundreds of participants per model), GeCCo can run multiple clients in parallel across a SLURM cluster. Clients share results via DuckDB on the shared filesystem, so the judge sees the full history from all clients.

Architecture

   OpenRouter (cloud API)
          | HTTP
   +------+------+
   |      |      |
 Client  Client  Client
  (CPU)   (CPU)   (CPU)
   |      |      |
   +------+------+
          |
   Shared filesystem
   (DuckDB state)

Clients access the LLM through OpenRouter (or your chosen cloud provider) — no GPU node needed. If you prefer to self-host a model, you can run a vLLM server on a GPU node and use --vllm-url instead.

Step 1: Define client profiles

In your config, add a clients: section. Each profile can override LLM settings like temperature, system prompt, and guardrails:

clients:
  exploit:
    llm:
      temperature: 0.3
      system_prompt_suffix: |
        Focus on refining the best-performing model.
        Make small, targeted changes.
  explore:
    llm:
      temperature: 0.9
      system_prompt_suffix: |
        Try fundamentally different architectures.
      extra_guardrails:
        - "Each model must use a mechanism not in any previous model."
  minimal:
    llm:
      temperature: 0.5
      system_prompt_suffix: |
        Propose simple models with few parameters.
      extra_guardrails:
        - "At most 3 free parameters."

Step 2: Launch the distributed run

Clients will use the LLM provider configured in the YAML (e.g. OpenRouter). No GPU setup needed:

# Launch all client profiles from your config
uv run python -m gecco run distributed \
    --config config/archive/two_step_factors_distributed.yaml

# Run only specific profiles
uv run python -m gecco run distributed \
    --config config/archive/two_step_factors_distributed.yaml \
    --profiles exploit,minimal

# Preview without submitting
uv run python -m gecco run distributed \
    --config config/archive/two_step_factors_distributed.yaml \
    --dry-run

# (Advanced) Point at a self-hosted vLLM server instead of a cloud API:
uv run python -m gecco run distributed \
    --config config/archive/two_step_factors_distributed.yaml \
    --vllm-url http://gpu-node:8000/v1

Step 3: Monitor progress

# One-shot status
uv run python -m gecco monitor --task two_step_factors

# Live dashboard (refreshes every 10s)
uv run python -m gecco monitor --task two_step_factors --watch 10

Step 4: Streamlit dashboard

An interactive web dashboard is available in gecco-mh-dashboard/. Install dashboard dependencies:

uv sync --extra dashboard          # install + dashboard extras
# or: pip install -r gecco-mh-dashboard/requirements.txt

Then run on the HPC compute node:

uv run streamlit run gecco-mh-dashboard/app.py \
    --server.address 0.0.0.0 --server.port 8501

# From your local machine (SSH tunnel through login node)
ssh -N -L 8501:<compute-node>:8501 <user>@<hpc-login-node>

Then open http://127.0.0.1:8501 in your browser.

How coordination works

  • Clients share results via DuckDB-backed canonical state on the shared filesystem
  • Before each iteration, clients merge cross-client history into their feedback
  • The global best model is tracked across all clients
  • File locking and atomic writes prevent corruption from concurrent access
  • The judge runs as a centralised orchestrator that analyses all client results at once

  shared_registry.duckdb.lock
  baseline.json            # Baseline model fit results
  diagnostics.duckdb       # Diagnostic store (per-client shards)
  models/                  # Generated model code (.txt)
    iter0_run0.txt
    iter1_run0.txt
    best_model_0_run0.txt

    iter0_run0.txt
    iter1_run0.txt
  reviews/                 # LLM code review outputs (.json)
    iter0.json

Understanding the output

Each bics/iterX.json contains the BIC values for every candidate model in that iteration:

[
  {
    "function_name": "cognitive_model1",
    "metric_name": "BIC",
    "metric_value": 245.67,
    "param_names": ["alpha", "beta", "w"],
    "code_file": "results/two_step_task/models/iter0.py"
  }
]

Lower BIC is better. The model with the lowest BIC across all iterations is the overall winner.

The judge LLM analyses the diagnostic store and produces feedback covering:

Parameter identifiabilityCorrelation matrix, recovery rates, degeneracy

Mechanism interpretabilityWhether the best models make sense theoretically
